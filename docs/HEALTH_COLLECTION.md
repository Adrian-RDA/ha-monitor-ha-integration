# System Health Report v1 – Sprint 6

Implemented in 0.4.0. The [Laravel contract](PROTOCOL.md#system-health-report-v1-sprint-6) is authoritative. Health is independent of heartbeat ingestion and Monitoring Snapshot v2. It neither creates local sensors nor calculates a health score.

## Consent and privacy

`health_enabled` defaults to false for new and existing entries. Once enabled, `health_sections` explicitly approves repairs, config entries, unavailable entities and/or native backup observations. Deselected sections are transmitted as `unsupported`, with null metadata and no findings. Disabling Health stops its collection as well as export; the general transmission switch pauses its upload while local Health collection continues.

Repairs and config-entry collection use `scope: all` within the approved section. Entity export defaults to `scope: selected`, with an empty selection. `health_entities` approves individual entity IDs; `health_all_entities` separately approves all enabled entities with an actual unavailable state, including hidden entities and entities without a registry entry. `health_devices` separately approves associations with opaque local device registry IDs. These options never enable an entity or integration.

All `name` fields default to null. `health_names` is a separate, default-off approval for config-entry titles, entity-registry `name`/`original_name` and device-registry `name_by_user`/`name`. Operator labels take precedence. Review these labels for private details and credentials before approving them; this is consent, not an automatic secret detector. Device names require both `health_names` and `health_devices`. No fallback to state `friendly_name` or other attributes is used, and unregistered entities keep null names. Repair names remain null: translated issue text/placeholders are not a safe registry-label source. Invalid/empty names, names over 120 Unicode characters, and control/format/private-use characters or line/paragraph separators yield null without losing the finding.

Source IDs and entity IDs can themselves describe private installation details; this is explained in the configuration choices. Only the contract's allowlisted fields leave HA. Config-entry data/options, repair placeholders/data, entity attributes, device hardware identifiers, logs, exceptions and backup contents/paths/keys are never included. Diagnostics expose quality, uploader status and timestamps without finding records or source IDs; the additional local backup evidence is explicitly historical. Existing local sensors and pairing storage remain unchanged.

## Collectors and source semantics

`health_collectors.py` contains transport-independent collectors:

- Repairs use `homeassistant.helpers.issue_registry.async_get`. Only active registry issues are included. Deleted or persisted-but-not-reactivated issues are absent. `dismissed_version` identifies ignored issues, matching HA's Repairs API. The original critical/error/warning severity is retained. Hidden issues associated with disabled entries remain repair observations; they do not manufacture config-entry failures.
- Config entries use `hass.config_entries.async_entries`. Loaded and deliberately disabled entries are excluded. Native `setup_error`, `setup_retry`, `migration_error`, `failed_unload`, `not_loaded`, `setup_in_progress` and `unload_in_progress` are preserved. The first four are failure observations; `not_loaded` is neutral and proves no failure, and the two progress states are transitional. The agent exports the native state without adding an error severity or domain-wide outage claim. Unknown future states cause partial coverage, never an invented failure. YAML-only failures are outside this contract.
- Unavailable entities use HA's state machine and entity registry. Only actual `unavailable` states on enabled entities qualify. `unknown`, missing states and ordinary `off` are not findings. A disabled registry entry's stale unavailable state is excluded. A missing selected state is not relabeled unavailable. Optional device association uses the device registry's local ID; the associated device may also own working entities. No device-offline assertion or installation-wide affected-device count is produced.
- Backup uses the existing native backup manager's public getter and event subscription. No extra integration, manually configured sensor, Supervisor HTTP request, filesystem scan or network call is required. The agent never loads the backup integration on behalf of the user. The manifest's `after_dependencies: backup` only orders setup when that integration is already configured.

Before `CoreState.running`, **no Health observation is created or queued**, including no report UUID/timestamp or synthetic neutral replacement. The official `async_at_started` helper releases an immediate real collection and the independent five-minute clock after HA has fully started. Reloading an already running HA also collects immediately. Repeated starts are idempotent; unload cancels the pending startup listener, clock, collection, history restore and uploader. Already queued callbacks and explicit collection calls after unload cannot restart collection. Heartbeat and Monitoring v2 lifecycle code is unchanged and runs independently while Health waits.

Each section and individual source is isolated. An unreadable record yields partial coverage and an unknown total while retaining known peers. A failed entire section yields `unavailable`, null total and no stale findings, then can recover on the next real tick. Unselected or unsupported sections are explicit neutral observations.

Source keys preserve contract-safe local identities, normally `domain:issue_id`, config-entry ID and device registry ID. Nonconforming keys use a deterministic SHA-256 digest salted by the paired instance UUID, without reading credentials. A device association is stable across reload/restart/renaming as long as HA retains the same registry entry. Deleting/recreating a device can change its identity. Device association is optional and limited to represented unavailable entities, suitable for central per-device ignore matching without exporting hardware identifiers. A config-entry identity never implies an entity-to-config-entry relationship that the v1 entity record does not carry.

## Backup evidence and limitations

The native API was inspected against HA **2026.10.4 and 2026.11.0**. Tests exercise the real installed 2026.11.0 `BackupManager`, `async_get_manager`, `async_subscribe_events`, `async_on_backup_event` and native event classes. A test also invokes the public `async_create_backup` failure path with a simulated failing backend. The 2026.10.4 source has the same relevant event/getter/subscription API; a full 2026.10 runtime test is not claimed.

`CreateBackupEvent` has `state`, `stage` and bounded native `reason`, but **no event timestamp**. The synchronous callback records UTC time when the native manager emits the initial `in_progress` event with `stage=None`. Intermediate stages do not advance attempt start. A terminal `completed` event supplies the observed completion time and status `ok`; a terminal `failed` event supplies `failed`. Both manual and automatic creations through that manager use this lifecycle. Restore, receive/upload and idle events do not imply successful creation. A running backup remains running without an arbitrary timeout policy.

Only complete lifecycles observed after subscription are classified. Initial load, reload, manager replacement or attachment during an existing run yields `unknown`, with null metadata. A successful completion observed before a later attempt is retained in the live collector as `last_success_at`, including across a subsequent failure within that continuous observation session. It means the last **known observed** successful completion; unobserved earlier successes cannot be reconstructed. Clock rollback that would invert timestamps or put them in the future clears the observation to unknown. Unload removes subscriptions and discards live collector state. Subscriptions may attach before HA is running so genuine native startup backup events are not missed; this does not release Health reports before HA is running.

`health_history.py` retains one bounded, confirmed terminal observation per config entry using HA's versioned `Store`, with private file permissions and atomic writes. Only status `ok`/`failed`, original observed/attempt/success timestamps and the bounded error code are saved. Running, unknown, partial lifecycles, raw events and raw reasons are never saved. A known older success may be retained in this local record after a new failure; it is still historical evidence, not a complete backup history. The file is `.storage/ha_monitor_agent.<entry_id>.backup`; HA storage is not automatically encrypted. No credentials, names, identifiers from backup contents, paths or backup data are stored there.

Restoring runs in a cancellable entry background task and never gates setup, collection or uploads. Live evidence wins a restore race. Exact-key schema, allowed statuses/codes, aware timestamps, ordering and future-time checks reject unusable saved data. Writes coalesce through HA's delayed-save helper (one second), flush on unload or HA's final-write event, and unload's flush is bounded to five seconds. Storage failure cannot erase a valid live observation or stop another worker. Persistence is best effort: hard termination before a write, clock rollback or disk failure can lose the latest evidence. Disabling backup Health stops new observations/storage I/O and retains the existing file; removing the config entry deletes it.

Saved evidence appears only in local diagnostics under `health.backup_history`, with `interpretation: historical_only` and its original timestamps. **It never seeds the live collector or Health-v1 payload**, even after a graceful reload: the native event API provides no durable attempt identity/timestamps with which to corroborate it, and an observation gap can hide later attempts. Current backup status and metadata remain unknown/null until a new full lifecycle is observed. Even a new live failure does not import a restored historical success into its wire metadata. No report buffers, credentials or backend observations are restored. The Health-v1 contract is unchanged.

HA's `last_attempted_automatic_backup` and `last_completed_automatic_backup` cover automatic backups only. They do not establish the latest manual attempt/outcome. The manager's `last_action_event` has no start/completion timestamps. Backup inventory dates are creation metadata, not proof that the latest attempt completed successfully. These sources are deliberately not combined into a purported complete history. Empty history does not prove `never`. External backups bypassing the native manager are outside the approved source.

Absent backup integration/API support yields `unsupported`; an expected manager that is temporarily unavailable yields `unavailable`. A loaded manager without sufficient evidence yields `unknown`. Exact native `backup_agent_unreachable` maps to `connection`; generic manager, reader/writer, upload and other failures map to `unknown`, because their cause cannot be classified more precisely from that code. Free-form text is never inspected, stored or exported. Other contract error categories remain available for future sources with reliable typed evidence. No overdue-backup or inferred-success rule is added.

## Report bounds and transport

`HealthCoordinator` schedules an immediate observation **once HA is fully running**, followed by a full observation every **300 seconds**, independently of HA entity polling, local sensors, heartbeat and monitoring workers. At most one collection task runs; slow ticks are skipped. Registry/state APIs execute on HA's event loop; JSON projection/encoding uses its executor. Each observation gets a new UUID and original UTC observation time.

Collectors keep a deterministic sorted subset using a bounded heap: **100 repairs, 256 config entries, 1,000 unavailable entities**. Collection overflow yields `partial` with the known full matching total, or null if that total is unreliable/outside the contract bound. Totals describe findings, not the entire HA inventory. Complete empty scope means a real zero within that scope.

`fit_report` measures the actual encoded envelope and trims the tail of unavailable entities, then config entries, then repairs until it fits **262,144 uncompressed bytes**. Each affected section becomes `partial` while preserving its known total. The local observation remains intact. There is one full replacement report per request, with every section and required null field present; no chunks or fragments.

`HealthUploader` reuses the existing verified client, acknowledgment validation and bounded worker mechanics. It has its own pending/latest frozen bodies, lock, timer, failure counter and backoff. Health uses `/api/v1/agents/health`, `schema_version: 1`; Snapshot v2 continues on its v2 endpoint. Two immutable reports maximum are retained; new unsent observations coalesce. Only `sent_at` advances on retry. Retry IDs, timestamps and content stay unchanged. Observations older than 23 hours or future-dated after a clock rollback are discarded.

Minimum request spacing is 15 seconds (at most four attempts/minute). Backoff uses bounded exponential jitter with a 900-second cap; longer valid `Retry-After` values are respected up to the shared 24-hour bound. Permanent errors, including 409, stop only Health and create a translated Repairs issue. Credential rejection starts shared reauthentication and prevents all further authenticated uploads; older in-flight acknowledgments cannot undo it. Verified shared HA HTTPS, bounded responses, no redirects with credentials and no payload logging remain in force.
